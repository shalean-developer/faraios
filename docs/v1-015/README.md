## Standard business export

`export-fields.json` is an explicit 17-dataset allowlist. `export-query.py` generates a single read-only SQL statement inside a repeatable-read transaction; it does not connect, read credentials, create a public endpoint or grant privileges. Use the existing approved operator database channel only after identity and authority have been verified. Its owner UUID predicate is a consistency check, **not an authentication mechanism**. Never expose this privileged query as an unauthenticated web/API service.

Generate with exact business UUID, verified owner UUID and `live` or `preview`. Generate separate exports if both environments are explicitly requested; never merge silently. The query includes the business row only when current owner matches, scopes every operational table by business/environment, and joins enquiry activity through its scoped parent. It selects explicit fields, omits quote/invoice share tokens, and has no pagination truncation. It uses no writes and no provider/mail calls. A false `scope_verified`, timeout, truncated response or failed row-count comparison is a failed export, not an empty successful export.

Save the complete JSON through the approved operator channel into a private non-web directory, restrictive file permissions, with case reference and SHA256. Check every dataset's count against its array length; check business/environment, expected records, linked correction history and omitted categories. Never save raw exports in Git, a public artifact, the web root or this evidence package. Review free text for accidental credentials and third-party data before release. JSON preserves numeric minor-unit amounts, identifiers and correction links; if CSV is needed, agree the selected datasets and neutralize spreadsheet formula cells. Do not relabel an unreadable or partial dump as a complete export.

The standard package is not a whole-system personal-data response: account profile, waitlist, time-off/scheduling, communications, shared-event and support/provider records may require supplements. Record every included/excluded category and why; do not close a broader request until each requested category has a result or an explained limitation. Recheck owner/recipient authority just before delivery. Agree a private transfer method (for example a recipient-restricted channel or encrypted package with separately conveyed key), retention/expiry and receipt. Do not assume a secure-download portal already exists. If no suitable private delivery method is available, hold the package and arrange one; do not fall back to a public URL. Record delivery, receipt, remaining questions and working-copy disposition. No customer delivery or disposal is authorized by this audit.

## Manual account restriction and closure

1. Verify identity/authority, exact account and business/environment, requested outcome and timing. Distinguish website withdrawal, staff revocation, temporary account restriction, closure and deletion. Do not accept an ambiguous “delete everything” as an executable scope.
2. Offer an export and settle its scope before closing access. Inventory open bookings/quotes, balances, staff memberships/invitations, public pages, confidential document links, queued/retrying communications and related provider copies. Agree how open service obligations will be handled; do not cancel jobs or erase balances implicitly.
3. Prepare a bounded action list and obtain the required owner authorization for actual changes. Existing website unpublish and membership/invitation-revoke controls are separate actions. Staff inactive alone does not prove login revocation. Account restriction/sign-out must use supported provider controls, with current behavior checked at execution; changing/deleting Auth records by ad hoc SQL is not this procedure.
4. Check retained sessions as well as fresh access. Account restriction can have a token/session validity window; never promise immediate universal revocation without evidence. Protect other businesses and any shared user access. Unpublishing does not revoke quote/invoice bearer links. Inventory and address links individually using a separately reviewed mechanism; if no supported mechanism is available, record the unresolved scope and do not claim full closure. Keep issued financial documents and audit evidence intact.
5. Review and separately authorize pending communication suppression/cancellation. Prevent new sends for the agreed scope and resolve in-flight/provider-accepted messages honestly; already sent copies cannot be recalled by deleting an account. Do not disable global workers or other tenants to close one account.
6. Verify the exact agreed website/access/document/communication outcomes, retained-record integrity, exclusions and other-business preservation. Send a closure result only with authorization. Record what remains, why, next review date and escalation. Do not label the account closed while required controls are unverified.
7. Treat deletion as a separate scoped decision with retention obligations, provider copies and recovery-copy implications reviewed. No destructive account action, purge, key rotation, account ban or live access change was performed or authorized in this task. This criterion documents the process; it does not claim a destructive closure rehearsal.
