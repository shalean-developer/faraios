## Exact phase order and actors

Every phase requires a durable private journal entry with nonce, input identity, actor, exit status, bounded time and redacted output. Stop on the first failure; never continue to the checkpoint.

1. **Preflight, before mutation.** Verify pinned Node/Docker bytes, Linux/amd64, context/daemon/boot identity, fresh complete container/network/volume inventory, available memory/disk, cached image manifests/configs, and file hash coverage. Refuse existing candidate names or labels. Enumerate ordered image init/migration files into the run specification and hash that specification. No protected archive, key, business export, staging password, real JWT, provider credential or Docker socket may enter the candidate.
2. **Create isolation.** Allocate a fresh nonce-labelled internal bridge and only fresh candidate containers. No host ports, host networking, extra network attachment, host bind mounts, devices, privileged mode or published service endpoint. The reviewed harness must positively test internal reachability and negatively test external reachability using a controlled synthetic sentinel; inability to prove isolation is a stop. No probes against real Supabase, Zoho or other business services.
3. **PostgreSQL initialization, alone.** Use the accepted keypath derivative, vendor entrypoint, fresh empty PGDATA, `POSTGRES_USER=supabase_admin`, database postgres, and explicitly empty USE_DBMATE. The initialization superuser is supabase_admin, expected OID 10. The packaged migrate.sh first establishes postgres, then executes the image init-scripts in lexical filename order as postgres, then packaged timestamp migrations in lexical order as supabase_admin. Capture the full ordered list, including image-specific SQL, not a hand-selected subset. Do not run the two upstream SQL files absent from the image. Optional schema injection must be absent. Explicitly inspect effective POSTGRES_HOST/socket selection so the vendor temporary server is reachable without exposing TCP outside isolation.
4. **PostgreSQL post-bootstrap gate.** Require vendor initialization complete, final PID1 server ready and SQL readiness. Read back actual role attributes/memberships, extension versions, event helpers and search paths. Verify postgres ends nonsuperuser with expected managed attributes, and auth/storage owners exist before starting their services. If packaged migrations do not produce current staging structure, record the exact difference and stop; no compensating superuser, ownership or GRANT patch to manufacture parity.
5. **Auth migrations.** Run the pinned binary's `auth migrate` command against only the candidate database as supabase_auth_admin, namespace auth, using fresh synthetic credentials. The pinned command uses embedded migrations and the auth.schema_migrations ledger. Verify the resulting exact 82-version set: the seven versions seeded by PostgreSQL initialization plus all 75 packaged Auth versions, not merely a count or latest version. Migration failure blocks service startup.
6. **Auth index worker.** Start the pinned Auth service only after migration success, as its nonroot supabase OS user. Configure IndexWorker.EnsureUserSearchIndexesExist=true and MaxUsersThreshold=0 explicitly; defaults false/0 do not create the required search indexes. Use `GOTRUE_INDEX_WORKER_ENSURE_USER_SEARCH_INDEXES_EXIST=true` and `GOTRUE_INDEX_WORKER_MAX_USERS_THRESHOLD=0`: the pinned loader calls envconfig.Process("gotrue", config), with split_words on the IndexWorker struct and both fields. The harness must test this mapping and record a redacted effective-config readback before launch; prohibit unreviewed .env/config-directory overrides. Wait for vendor index-worker completion and read back all four user search indexes, including definitions, owners, predicates, indisvalid and indisready. Concurrent index creation must run through the worker, outside a wrapping transaction. No manual CREATE INDEX repair.
7. **Storage migrations through 0073 only.** Use the pinned tenant runner as supabase_storage_admin, after PostgreSQL's storage schema/bootstrap and roles exist. Set DB_INSTALL_ROLES=false, DB_SUPER_USER=postgres, DB_ALLOW_MIGRATION_REFRESH=false and DB_MIGRATIONS_FREEZE_AT=revoke-grants-to-unused-operations. The harness must prove its actual invocation passes upToMigration=revoke-grants-to-unused-operations; the environment setting alone is insufficient because the runner slices only when upToMigration is supplied. Keep single-tenant mode and disable optional vector/multitenant/queue services. Require exact ledger id 0 plus ids 1–73, matching names and hashes. 0074 unlock-object-versioning must remain unapplied and absent from the ledger. Fail on gaps, extra rows, refreshed hashes or a runner path bypassing the freeze.
8. **Storage grants and service gate.** Verify 0046's storage.super_user=postgres and 0049's bucket/object grant-option results using exact owner/grantor/grantee/privilege tuples. The actor remains the owning Storage migration role; no hand-written postgres grant. Start the service under a verified nonroot UID/GID with a fresh tmpfs file backend and synthetic JWT material. Verify local health and authenticated synthetic allowed/denied requests without any hosted endpoint or external object store.
9. **Synthetic compatibility readback.** Take a repeatable-read catalogue projection and compare all managed structures and the separate inactive-custody definition as described below. Exercise bounded synthetic fixtures and clean them. Capture a second stable projection. A ready server or green health endpoint alone cannot pass this phase.
10. **Cleanup and reconciliation.** Complete the protocol below before issuing a compatibility result. Only then may a separate checkpoint-use proposal be prepared. Never restore into or repurpose this synthetic candidate as an implicit continuation.

## Isolation and resource budget

Proposed maximum concurrent services: PostgreSQL, Auth and Storage, plus one short-lived synthetic probe. One CPU and 64 PIDs per container; memory/swap limits equal at 512 MiB each, maximum aggregate 2 GiB. Wall-clock bound 15 minutes, individual SQL 60 seconds, process/startup 180 seconds, stop grace 10 seconds. These are proposed limits; exceeding them fails the attempt and requires an explicit reviewed revision, never an automatic increase.

All roots read-only, all capabilities dropped, no-new-privileges, nonroot users. PostgreSQL UID:GID 100:101 retains the accepted tmpfs policy: PGDATA 384 MiB mode0700, PostgreSQL socket directory32 MiB mode0775, /tmp32 MiB mode1777, all noexec/nosuid/nodev. Auth UID1000 and Storage's numeric user/group plus writable paths must be verified from image contents before constructing the final arguments. Auth/Storage tmpfs budgets must fit their 512 MiB cgroups and aggregate limit. Failure under read-only/noexec constraints is evidence to review, not permission to relax them.

Generate fresh random database passwords/JWT material privately for this candidate only. Bind credentials to candidate-local DNS names and database, restrict filesystem mode0600, exclude from logs/argv/public evidence and Git, and destroy with cleanup. The operator's Docker-root visibility is part of the local trust boundary. No real user registration, email, SMS, OAuth consent, provider dispatch, financial record or live secret. Deny outbound hooks, SMTP, telemetry and remote storage configuration; network isolation must remain effective even if a service attempts an outbound request.
