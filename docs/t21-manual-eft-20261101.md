## Smallest complete implementation

- Business-owned immutable evidence receipts: unique request ID, business bank transaction ID, controlled evidence reference, positive ZAR amount, receipt date and recording actor/time.
- Separate explicit bank verification records verifying actor/time. Recording payment advice alone leaves payment unpaid. Verification alone leaves money unmatched.
- A verified receipt can match one same-business invoice. Multiple receipts support partial/full payment; excess cash remains unmatched. Duplicate IDs with changed facts and duplicate bank transaction references are rejected. No split receipt, refund, payout, bank feed, evidence attachment storage, notification or Zoho write is added.
- Shared invoice/booking payment projection uses verified manual allocations plus existing T20 verified credits. It does not mutate immutable invoice agreements, Zoho draft status, service status or earnings. Both detail pages use this same projection.
- Owners/managers only: current database membership, active business and live Auth session. Private tables have RLS enabled and no browser/service-role table grants. Narrow invoker public RPC delegates to a restricted definer with empty search path. HTTP requires authenticated office membership, exact form fields, same Origin and bounded body. List pagination retains access to older unmatched receipts.
- Payment-mode conflict guard: manual allocation is held if ANY online attempt already exists for that invoice, including failed attempts that could succeed late. New online intents are held once EFT is allocated. This is deliberate review of an uncertain financial outcome, not permission to remove existing attempts. A T21 trigger on T20 intent insertion is necessary to enforce this boundary atomically. Existing T20 account, backend, provider and credential configuration remain unchanged.
- Writers lock the existing invoice and update a shared per-invoice revision row. The revision update is intended to force stale REPEATABLE READ writers to abort. Real independent-connection concurrency acceptance is still required; single PGlite connection tests do not prove that outcome.
