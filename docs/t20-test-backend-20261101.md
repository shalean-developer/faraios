## Audit and decision

Read-only staging metadata confirms private_t20 and t20_payment_verifier are absent. Existing Auth columns sessions.id/user_id/not_after and users.id/banned_until exist. T19's backend client and credentials are limited to accounting RPCs. Keep them unchanged. Prepare a separate T20 Auth principal with no business membership, independently enrolled against exact business/account metadata. No broad service-role/JWT-signing key or direct database connection is needed. No new authentication foundation or custody application is introduced.

Official references checked: https://supabase.com/docs/guides/database/functions and https://supabase.com/docs/guides/auth/sessions . ## Candidate components

- database/t20-payment-https-candidate.sql follows the prior store candidate. It adds a private backend-account enrollment table, a live-session check, owner/manager commands and backend lookup/publish commands. Backend rows default disabled; no principal/enrollment is inserted.
- Public wrappers are SECURITY INVOKER with PUBLIC/anon/service_role execution revoked. Private implementations use fixed empty search paths and narrowly scoped SECURITY DEFINER access to existing Auth/session and private payment records. Every call checks actual session existence/expiry and banned status. Backend publication additionally requires no active business membership and an enabled exact principal/business/account mapping to an enabled active business account. Merely being authenticated is insufficient. Account configuration is owner-only; intent/status access is owner/manager scoped. Unwrapped private owner functions lose authenticated execution so live-session checks cannot be bypassed through them.
- src/t20-payment-backend.js uses the existing SDK and fixed staging HTTPS origin. Its transport permits only password/refresh/current-user/local-signout Auth requests and t20_payment_backend. T19/owner/table/provider routes, foreign origins, alternate schemas, redirects and oversized responses are rejected. Errors are fixed/redacted. Principal identity is checked at login and refresh; concurrent refresh is single-flight; close signs out only the dedicated session. Import performs no configuration read beyond existing public staging metadata, secret access or network operation.
- database/t20-payment-empty-rollback.sql removes only named T20 objects in reverse dependency order without CASCADE, and only if all T20 tables are empty and the verifier role has no members. Any existing payment/account data blocks rollback and must be reviewed separately. No T19 or existing public invoice object is removed.

The database interface trusts its future authenticated backend to supply observations only after signature/API verification. This privileged boundary is deliberate; a compromised verifier can fabricate observations. It has no bank/card/charge API or provider secret in SQL. Deployment must retain the dedicated principal and private server-only credential boundary. The client is not a browser API and must never be bundled or return credentials to the owner UI. Backend enrollment is operator-controlled, not user-editable JWT metadata.
