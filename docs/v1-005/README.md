## Reproduction and repair

`tests/scheduling-baseline.py` uses the immutable installed V1-017 SQL: two overlapping jobs for one worker both commit; the overlap appears only afterward. This is intentionally a before-repair test, not evidence that old scheduling is safe.

The bounded candidate adds explicit owner scheduling settings, weekly hours and fixed before/after buffers. Thirty minutes before and after means sixty minutes between jobs. There are no implicit working-day defaults. One interval per day is supported; split overnight hours between days. Submitted worker time-off requests block new strict assignments. The owner may resolve a withdrawn request with a reason; the request is retained with a separate resolution record.

All enabled-scope assignments, reschedules, direct APIs, delegated commands and worker time-off writes share one outer business/environment lock. A versioned scope row also rejects stale REPEATABLE READ snapshots; advisory locks alone do not establish that guarantee. Database triggers validate every added worker and full occupied interval before any final assignment or schedule save. Multiworker writes roll back entirely on conflict. Absolute instants, saved booking zones, local-day windows and existing DST gap/fold rejection are retained. Pending requests and unallocated bookings promise no worker capacity. No automatic confirmation, route calculation, specialist resources, recurring dispatch or expanded permissions are added.

Installation enables **no policy** and rewrites no business, booking, assignment, document or financial row. Owners explicitly opt in. Activation requires acknowledging existing active work; its exact schedules/assignments are retained as legacy obligations. Keeping an existing link through `INSERT ... ON CONFLICT` does not accidentally revalidate or remove it. Adding a worker or changing/reopening a schedule must meet strict rules. New conflicts still include legacy jobs. Config changes cannot silently invalidate strict jobs; safeguards cannot be disabled while strict assigned work remains unresolved. Inactive staff and revoked login access do not silently release an existing reservation.

## Guarded rollback and rollout gate

Rollback must retain every new table, history row, resolution and the common locking/validation functions. Never drop scheduling state, restore an old database or replace old writer functions while strict scheduling is in use. `rollback_ready` refuses an incompatible UI downgrade while any strict policy is enabled. Resolve outstanding work and explicitly disable strict operation through the owner API before considering a bounded guarded reversion of the three old UI files. Keep the additive settings page and database objects available for administration and forward repair. File preflight rejects later concurrent edits before any replacement. The rehearsal proves rejection and successful bounded reversion preserve all database fingerprints. A production deployment still needs immediate private preimages, current file/function guards and separately reviewed exact authorization.
