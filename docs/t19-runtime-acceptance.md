## Source integration

`t19-custody-runtime.sql`, `t19-custody-oauth.sql` and `t19-custody-api.sql` are review source in that order, following the unchanged inactive Issue140 proposal and existing invoice foundations. They are not generated Supabase migrations and are not imported by deployment scripts. The explicit review-context guard is not an approval. A future generated migration requires exact-SQL approval, grants review, restore checkpoint and the applicable Supabase checks.

The runtime SQL proposes revoking **all ordinary REST/worker grants on Vault tables/functions**. Before approval, inventory every Vault consumer and confirm that no completed application depends on those grants. The new minimal function owner needs only decrypted-view read and secret creation. It receives no LOGIN and callers receive no membership in it. Native superuser fixture role assignment does not prove managed Supabase role-assignment permissions. These are material deployment/security gates, not assumed successes.

`connectCustodyPostgres` accepts explicit configuration only; no service-role or environment URL fallback. `createRestrictedAccountingService` constructs an mTLS server without listening. The worker submits only an operation ID. `createAccountingProxy` revalidates the existing web session and forwards only its Auth access token, opaque session correlation and selected request fields over verified mTLS. Browser authorization/identity headers are never forwarded. The isolated process uses a publishable-key client, verifies the token with Auth and reloads database memberships for every session read. No cross-process session Map or refresh-token transfer is required. Operational TLS/database/Supabase configuration remains explicit and unprovisioned. The service has no implicit login endpoint or scheduler.

Owner UI is available through the new handler at `/accounting/:business/connection`; it shows connection state, pending revocation, synchronization failures and explicit reconciliation. The existing staging server accepts an optional accounting proxy, mounts these routes, links connection settings and enqueues invoice work through authenticated RPCs. It rejects combining the new proxy with the legacy worker and refuses it in restore mode. No entrypoint supplies the proxy, so existing staging remains inactive. The host supplies its actual session-cookie name. The main Strict cookie is preserved; a five-minute HttpOnly callback-path Lax cookie supports the provider return. Both state digest and session digest must match, and the callback cookie is cleared on return. Tokens and codes are never reflected into the page.

## Verification

Consolidated focused command covers custody database/OAuth/API/worker, core, machine, operation and provider tests plus the existing Zoho invoice checks. It uses mocked provider responses and test-only secret values. The SQL tests use actual PostgreSQL semantics through PGlite, including table/function grants and RLS; they do not prove Supabase Vault encryption. The Vault test substitute is explicitly plaintext and confined to disposable databases.

The final local consolidated run passed **84 tests, zero failures and zero skips**, including the bridge and existing auth/invoice regressions. `npm run check` and whitespace checks passed; CI verifies the final committed source.

Automated review identified and prompted fixes for three recovery defects: revoked actors starving a shared worker pass, expired undispatched refresh claims remaining stuck, and definitive invalid grants being misclassified as uncertain rotation. Targeted SQL/worker regressions now verify current-authority queue filtering and per-operation failure isolation, fresh leases that fence stale dispatch, no replay after refresh dispatch, and renewed owner consent after a definitive rejection. Uncertain outcomes retain the independent recovery hold.

`node scripts/run-t19-custody-postgres.mjs` creates its own empty local PostgreSQL cluster, strips inherited database credentials, runs the two-business invoice scenario with the same source SQL/adapters, and removes the cluster. Native PostgreSQL 17.10 passed locally: two independent concurrent sessions yielded one successful invoice claimant; an expired undispatched claim safely retried; a lost response after creation required reviewed read-only reconciliation; two business totals matched with two total POSTs. Native runner cleanup was confirmed. The initial sandbox attempt failed on an initdb WAL rename; the approved isolated run outside that Windows sandbox passed. The loopback HTTP/TLS tests likewise require a sandbox profile permitting local sockets.

Foundation CI now invokes this new native scenario in addition to the existing full suite/native checks. Exact final commit, check runs, GitGuardian and automated-review disposition are recorded on the PR and canonical tracker. Automated review is not the independent human Issue140 assessment.

The new bridge test exercises the actual staging login/session, HTTP proxy, real generated-certificate mTLS listener and custody membership adapter. It verifies that attacker-supplied authorization/session headers are replaced, manager disconnect is denied, revoked membership stops access, and restore/legacy-worker combinations are rejected. Auth/provider responses in that test remain mocks. Background scheduling can invoke the authenticated `/custody/run` endpoint with an empty object; it derives due operation IDs from current machine grants and processes at most 20. No scheduler is installed or enabled.

## Specific remaining blockers and limitations

1. **Governance:** this PR needs its own applicable review/merge decision. PR141/142 exceptions do not extend to it. No auto-merge is configured.
2. **Issue140/A12:** appoint an independent human assessor, obtain attributable SHA-bound PASS, then obtain separate owner approval of the exact inactive SQL. The new runtime SQL/grants require their own review and exact-SQL approval; the inactive proposal does not authorize them.
3. **Deployment integration:** approved managed-role provisioning, protected database/machine credentials, upstream mTLS and session validation, route mounting and worker scheduling remain unprovisioned. No host configuration or production deployment is included.
4. **Provider acceptance:** real OAuth, effective CREATE permission, revocation, refresh, two-business isolation and totals are unverified. The revoke implementation uses a form-body token parameter and requires provider acceptance; mock success does not establish that Zoho accepted it. OAuth only probes read operations; it never fabricates CREATE-permission evidence.
5. **Recovery requiring human evidence:** uncertain refresh rotation, uncertain provider revocation and rejected/late grants stay quarantined. This source deliberately has no generic “clear quarantine” or automatic replay. Resolution needs the reviewed provider/credential evidence and an approved, scoped action. Historical invoice jobs from a retired generation stay fenced and need an explicit reviewed reconciliation disposition; reconnect does not rewrite their generation.
6. **Existing scope limitation:** VAT-enabled invoice sync remains held until verified tax mappings exist. This change does not invent tax rules or T20/T21 payment behavior.

T19 remains **In progress**; A12 unresolved; accounting activation **NO-GO**; T20 **Not started**. Source tests and merged foundations alone cannot satisfy full T19 acceptance.
