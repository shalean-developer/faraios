| Quote ready | New owner-reviewed customer notice containing only that quote's existing confidential link, currency, deliberate document total and expiry. |

## Exact implementation

`release-scope.json` pins ten runtime files: five bounded replacements (owner Bookings, Quotes, Invoices, Enquiries and core's allowlisted communication errors) and five new files (owner Messages page, pure template/dispatcher, private configuration/HTTP adapter, signed delivery webhook and CLI worker). Existing owner pages gain only Review messages links; enquiry outcomes also show failure reasons and safe recovery guidance. No role permissions or public content change. The new Messages page is owner-only and bounded to 20 displayed rows/page.

`install.sql` is one additive transaction. It adds four RLS-protected, directly ungranted tables to the existing backed-up authorization_private schema; four capture triggers; three private helpers; two owner APIs and three service-only worker/delivery APIs. It replaces no existing function, table, policy, data, global gate or schedule. Capture requires a named operator scope row, initially none. Every captured event starts review-only or blocked; no trigger queues a send. Scope+outbound+recipient allowlisting, current owner and current record are rechecked when approving and claiming. Credentials stay private. The separate worker configuration and recipient list are also default-off/empty. No worker schedule is installed.

The stable provider key is lifecycle/environment/job-ID. Immutable payload/recipient and template source must remain stable throughout the retry window; do not deploy a template/config-base change over pending/unknown sends. Attempts use a two-minute lease, at most five attempts, exponential delay and a 20-hour first-attempt / 24-hour creation cutoff inside the existing provider-retention contract. A lost acknowledgement retries the same bytes/key. A permanent rejection, invalid recipient or expired/uncertain send requires support review instead of an unsafe new send. Existing issuer/guest APIs retain their original token-purpose checks.

Delivery uses the existing HMAC/timestamp verification contract (a self-contained helper avoids a preview dependency on waitlist files/configuration) with a separate private webhook secret and service-only receipt API. Signed receipts may precede finish acknowledgement; replay is idempotent, conflicting IDs reject, and a later/out-of-order delivered event cannot erase a bounce/complaint/failure. Provider acceptance is explicitly not inbox delivery. A receipt signals provider delivery, not that a person read the message. The short dispatch race after a claim cannot retract an already submitted provider request; revocation stops subsequent claims/retries. Reconcile any in-flight outcome rather than claiming retroactive cancellation.
