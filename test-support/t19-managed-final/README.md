# Synthetic managed metadata overlay

Scope: T19 isolated candidate only, after Storage 0073 and before strict managed comparison. No hosted migration, archive restore or operational custody installation.

The PgBouncer body derives from the public Supabase PostgreSQL get_auth definition retained in ../t19-bootstrap-helpers/upstream-before-cron-cascade.sql (license in that directory). get-auth-before.sql preserves the pinned image's definition. get-auth-expected.sql preserves the formatting/case observed in the owner-authenticated staging capture; the role lookup expression is unchanged. CREATE OR REPLACE retains its OID, owner, existing execution ACL, SECURITY DEFINER and empty search_path. No function execution result or role password is captured.

The owner-host run /root/t19-bootstrap-run-gXNDORWm passed isolation, PostgreSQL, helper hardening, btree_gist, Realtime, Auth migrations/indexes and Storage. Its strict catalog diff identified only this function body and the explicit owner grant options on storage.buckets and storage.objects. Sixteen self-grant flags were false locally and true in staging. The overlay makes those two tables' eight owner privileges explicitly grantable; PostgreSQL object owners already possess implicit grant options. No browser/service role grant changes are permitted. RLS stays enabled and unforced, tables must be empty, owner/grantor stay supabase_storage_admin.

overlay.sql refuses absent synthetic context, a non-bootstrap user, a non-postgres database, a non-PG17 server, preexisting custody or unexpected initial definition/owner/grant flags. It validates preserved function metadata and non-owner table grants within the same transaction, then the complete managed catalog must still match. Any failure rolls back this overlay; the harness retains normal cleanup and evidence gates. It does not normalize away or exclude metadata differences.

The native PG17 CI fixture executes the exact overlay and checks definition/ACL changes, denied context, role lookup for a nonexistent synthetic login and transaction rollback. The embedded PG18 test proves version rejection without changes; it is not reported as PG17 success. Owner-host compatibility remains unverified until a new source-bound signed run passes every gate. Historical evidence is unchanged; the protected restore project remains untouched and T20 is excluded.
